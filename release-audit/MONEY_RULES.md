**Scope:** read-only source audit of application code on `main`, plus read-only inspection of Supabase project `ttvdpgxqvvtjnxxfkoui`. ## 1. Final rules table

Amounts are stored in minor currency units. “Period” means the selected report range, not an all-time ledger balance. A “+ / −” means an increase/decrease in that measure.

| Event / operation | Gross Sales | Net Sales activity | Cash / online totals | Credit outstanding | Coupon balance | Expected cash |
|---|---|---|---|---|---|---|
| Merchandise sale (`RECORD_SALE`) | + original sale amount | + original sale amount | + each Cash / Online funding part only | + credit-funded part in the authoritative credit ledger | − coupon-funded redemption part | + Cash funding part |
| Credit repayment (`RECORD_CREDIT_REPAYMENT`) | 0 | 0 | + repayment amount in its actual Cash / Online tender; coupon repayment is not external cash | − amount allocated to debt | coupon balance decreases if coupon pays the repayment | + Cash repayment part |
| Coupon purchase / top-up (`RECORD_COUPON_PURCHASE`) | Does not enter the merchandise-sale inflow metric | Coupon purchase/top-up is reported separately from merchandise net-sales activity | + actual Cash / Online funding parts only | 0 | + purchased/top-up ledger value | + actual Cash funding only |
| Coupon redemption | Already included in underlying merchandise sale; no second sale | No additional net-sales effect | No separate external receipt; any Cash / Online remainder is part of the merchandise sale | As determined by the underlying sale's credit part | − redeemed coupon value | + only any Cash remainder |
| Coupon promotion bonus | 0 | 0 | 0 | 0 | + bonus value | 0 |
| Refund (`RECORD_REFUND`) | Original sale stays in original Gross Sales | − refund amount in the refund event's period | − only actual Cash / Online refund destination parts | Unpaid-credit return reduces debt without a Cash / Online payout; paid excess is refunded according to supported destination | + only when refunded to coupon wallet | − actual Cash refund payout only |
| Void (`RECORD_VOID`) | Original sale remains in the original sale-origin metric | − amount reversed, in void event period | − supported Cash / Online reversal parts | Credit-funded sales are not supported by the void validator | Coupon-funded sales are not supported by the void validator | − supported Cash reversal only |
| Amount correction (`RECORD_AMOUNT_CORRECTION`) | Original sale amount remains the original sale-origin measure | +/− signed correction delta in correction period | +/− corresponding supported Cash / Online funding delta | Authoritative ledger reflects credit change where supported | Not treated as a general coupon reclassification | +/− supported Cash lifecycle delta |
| Payment-method change (`RECORD_PAYMENT_METHOD_CHANGE`) | 0 additional | 0 additional | Reclassifies supported tender funding; paired movement should net to zero across Cash + Online | No change | Coupon-funded changes are unsupported | Any persisted Cash classification adjustment is included by the shift calculation |
| Expense (`RECORD_EXPENSE`) | 0 | 0 | Reduces the actual Cash or Online total | 0 | 0 | − Cash expense only |
| Expense correction (`RECORD_EXPENSE_CORRECTION`) | 0 | 0 | Signed lifecycle delta is applied in the correction event's period | 0 | 0 | Cash lifecycle delta only |
| Expense void (`RECORD_EXPENSE_VOID`) | 0 | 0 | Reverses the prior expense effect in the void event's period | 0 | 0 | Reverses prior Cash expense effect only |
| `OPEN_CASH_SHIFT` | 0 | 0 | Stores opening-count evidence; it is not added to collected sales/receipts | 0 | 0 | Opening count is **not included** in expected cash |
| `COUNT_CASH_SHIFT` | 0 | 0 | Stores a physical counted-cash observation; not a receipt | 0 | 0 | Does not change expected cash; compares counted with expected |
| `CLOSE_CASH_SHIFT` | 0 | 0 | Stores shift-close evidence / reconciliation snapshot | 0 | 0 | Does not itself create sales or settlements |
| Document/admin-only operations | 0 | 0 | 0 | 0 | 0 | 0 |

**Code anchors:** reporting rules are in `app/src/main/java/com/dailymoneyregister/feature/reporting/data/ReportingAggregator.kt:26–29, 68–105, 146–175, 190–264`; report input rows and event mapping are in `app/src/main/java/com/dailymoneyregister/feature/reporting/data/ReportingReadRepository.kt` and `ReportingRowMappers.kt`. Expected cash is `app/src/main/java/com/dailymoneyregister/feature/register/data/RegisterShiftReportReadRepository.kt:39–62`; Day Closing difference/status is `app/src/main/java/com/dailymoneyregister/feature/register/ui/DayClosingPresentation.kt:32–60`. Credit balance is the signed ledger sum in `app/src/main/java/com/dailymoneyregister/core/database/dao/LedgerDao.kt` (query `getCreditBalance`); coupon ledger signs are `app/src/main/java/com/dailymoneyregister/core/model/enums/ModelEnums.kt` (`CouponLedgerType`).

## 2. Confirmed behaviors

### Credit outstanding: report screens versus customer balance

- The production repository call to the aggregator is `ReportingReadRepository.kt` and calls `ReportingAggregator.build(ordered)` without the optional `creditOutstanding` argument. The argument defaults to `null`; the aggregator then computes `max(0, period credit sales − period Cash repayments − period Online repayments − period coupon repayments)` from the rows passed to that report. It is a **selected-period activity approximation**, not a running balance across all days. The clamp at zero is explicit in `ReportingAggregator.kt:255–264`. Other `build` calls are test calls; some tests pass an explicit balance. Search/source: [ReportingReadRepository.kt](https://github.com/guruoshan/Paid-Due/blob/main/app/src/main/java/com/dailymoneyregister/feature/reporting/data/ReportingReadRepository.kt), [ReportingAggregator.kt](https://github.com/guruoshan/Paid-Due/blob/main/app/src/main/java/com/dailymoneyregister/feature/reporting/data/ReportingAggregator.kt), [ReportingAggregatorTest.kt](https://github.com/guruoshan/Paid-Due/blob/main/app/src/test/java/com/dailymoneyregister/feature/reporting/data/ReportingAggregatorTest.kt).
- **Reports and PDF:** the Reports summary uses that aggregator output; PDF reads `readModel.summary` and prints `summary.creditOutstanding` at `app/src/main/java/com/dailymoneyregister/feature/reporting/pdf/ReportingPdfActions.kt:127–155`. Recent and History are activity lists, not this report summary, so they show the recorded sale/repayment events rather than computing a separate running credit figure. Relevant Recent activity types are declared in `app/src/main/java/com/dailymoneyregister/core/model/financial/RecentFinancialActivity.kt:15–26`; report rows are selected by event time in `ReportingReadRepository.kt`.
- **Customers:** yes, Customer Detail shows an outstanding balance. `CustomersViewModel.kt:326–340` calls `RegisterRepository.getCustomerCreditOutstanding`; `RegisterRepository.kt:2761–2798` obtains the balance from `ledgerDao.getCreditBalance(customerId, currencyCode)`; `LedgerDao.kt` sums all signed credit ledger events for that customer and currency, across dates. This is a running ledger balance, not period math. The UI formats it in `app/src/main/java/com/dailymoneyregister/feature/customers/ui/CustomerDetailScreen.kt` (the displayed field is `state.creditOutstandingMinor`).
- Example (amounts OMR):
  - **Day 1:** credit sale 3.000. A report whose selected range includes Day 1 and that sale but no repayment shows Credit Outstanding **3.000**. Recent shows the sale; History shows the sale. Customer Detail shows **3.000**.
  - **Day 2, no activity, report range Day 2 only:** the report/PDF selected-period calculation is **0.000**, because there is no Day 2 credit sale and no Day 2 repayment. Recent/History have no new activity; Customer Detail remains **3.000**.
  - **Day 3, repayment 3.000 cash, report range Day 3 only:** report/PDF show **0.000** (period credit sales 0.000 minus period repayment 3.000, floored at zero). Recent/History show the repayment event; Customer Detail shows **0.000** after the authoritative ledger repayment.
  - **Range Day 1–Day 3:** report/PDF compute 3.000 credit sales − 3.000 repayments = **0.000**. A range covering Day 1–Day 2 shows **3.000**. Thus reports do not consistently show point-in-time outstanding for arbitrary ranges; Customer Detail does.
- Credit balance is not stored as an editable customer field: `RegisterRepository.kt:2756–2798` and `LedgerDao.kt`'s `getCreditBalance` query establish the authoritative signed-ledger read.

### Opening float and Day Closing

- `OPEN_CASH_SHIFT` persists an opening cash count as shift-event evidence; see `app/src/main/java/com/dailymoneyregister/core/database/entity/CashShiftEntities.kt` and the `OPENED` event writer in `app/src/main/java/com/dailymoneyregister/feature/register/data/RegisterRepository.kt` (cash-shift lifecycle handling around the operation recovery/read path). The Day Closing expected-cash formula has no opening-float parameter: `RegisterShiftReportReadRepository.kt:39–62` is exactly Cash sales + Cash credit repayments + Cash coupon funding + Cash lifecycle adjustments − Cash refunds − Cash expenses.
- Day Closing displays expected, counted, difference, and a sign-based status: `DayClosingPresentation.kt:32–60`; difference is counted minus expected, and positive means OVER.
- Example: opening count 20.000, cash sale 5.000, counted cash 25.000. Code-derived expected cash = **5.000** (opening count excluded); counted = **25.000**; difference = **+20.000**; status = **OVER**, not EXACT. This is the observed behavior, not an assertion that it is the desired cash-control policy.

### Voids: credit-funded and coupon-funded sales

- `VoidFinancialIntegrity.kt:162–206` rejects a coupon-purchase transaction, any sale settlement containing Coupon, and a credit-funded sale with typed unsupported-operation exceptions. `TransactionActionEligibilityResolver.kt:95–105` uses the same validator to derive void eligibility, so the Void action can be unavailable before a submit attempt. `RegisterRepository.kt` also calls the validator during execution. Exact UI message depends on the exception-to-UiText mapping in `RegisterViewModel.kt`; the validator's type alone does not prove the displayed text is clear.
- **Credit sale:** Void is not an allowed correction. Use the supported refund path for a return; an unpaid-credit refund reduces the debt without inventing Cash/Online outflow. If the original amount/price is wrong rather than the sale being returned, amount correction is the separate correction path, subject to its validation rules. Tests in `RefundFinancialCoreIntegrationTest.kt` include `productionRefund_unpaidCredit_reducesDebtWithoutCashOnlineOrCoupon`; correction validation is `AmountCorrectionFinancialIntegrity.kt`.
- **Coupon-funded sale:** Void is also rejected. Use refund-to-coupon where the intent is to restore wallet value; this records a coupon refund credit. Do not use a cash refund to manufacture a cash settlement for coupon funding. The combined test `CouponSaleIntegrationTest.kt:178–209`, `partialRedemptionAndRefundToCouponAreAtomicReplaySafeAndVisibleInReadModel`, asserts coupon+cash redemption, partial refund to wallet, replay idempotency, and wallet balance restoration.
- **Clarity finding:** the source contains distinct exception types, but this audit did not confirm the exact end-user message text for both blocked cases from a complete UI mapping. Treat message clarity as **unverified**, not confirmed clear.

### Coupon plus Cash split and rounding

- Split creation occurs in `RegisterRepository.executeCouponRedemption` (`app/src/main/java/com/dailymoneyregister/feature/register/data/RegisterRepository.kt:306–380`), driven by `CouponRedemptionCommand.amountMinor` and `remainderCategory` in `app/src/main/java/com/dailymoneyregister/feature/register/data/CouponSaleCommand.kt:65–95`. The selected coupon amount is an integer minor-unit amount; the remainder is the sale total minus coupon amount and is assigned to the selected Cash, Online, or Credit category. The financial writer persists funding parts; report aggregation consumes those persisted parts in `ReportingAggregator.kt:68–105`.
- Example covered by `CouponSaleIntegrationTest.kt:178–209`: sale total 7.000, coupon funding 3.000, Cash remainder 4.000; the wallet falls from 5.000 to 2.000 and the sale funding breakdown is exactly Coupon + Cash. A subsequent 1.000 refund to Coupon raises the wallet to 3.000.
- The audited split path uses integer minor units and exact arithmetic; no floating-point rounding is required for this coupon-versus-remainder allocation. Tax rounding is a separate sale-total calculation and the branch/business rounding mode is stored on Branch (see `branches.tax_rounding_mode` in the live schema). I did not find a test establishing every tax rounding mode's end-to-end behavior for a coupon split.

## 3. Known gaps and open questions

1. **Report Credit Outstanding is not a point-in-time balance.** Production reporting does not pass the authoritative customer ledger balance to the aggregator. A one-day report can show 0.000 on Day 2 while the customer still owes 3.000. Decide whether Reports/PDF should display selected-period net credit activity or an as-of ledger balance; these are different measures and should not share an ambiguous label.
2. **Opening float is excluded from expected cash.** With opening 20.000, cash sale 5.000, and counted 25.000, Day Closing says expected 5.000 / counted 25.000 / difference +20.000 / OVER. Confirm whether this is intended or whether expected cash should include the opening count.
3. **Void message clarity is not verified.** Validator rejects both credit-funded and coupon-funded sales, but exact final user-facing messages were not confirmed end-to-end. Clarify the intended action text: refund/credit adjustment for credit sales; refund-to-coupon for coupon-funded sales.
4. **Coupon bonus coverage is projection-only in tests located.** No end-to-end bonus issuance test was found in the reviewed set.
5. **Cash-shift lifecycle test gap.** No dedicated OPEN/COUNT/CLOSE persistence/replay integration test was located; only expected-cash helper tests were found.
6. **Expense lifecycle test granularity.** One combined integration test covers correction and void; reporting has separate projection tests, but no separate correction-only/void-only lifecycle test was located in `ExpenseIntegrationTest.kt`.
7. **Tax rounding / split tender.** Coupon-vs-remainder allocation is in integer minor units, but end-to-end tests for all configured tax rounding modes combined with split tender were not located.
8. **Live migration ledger:** Supabase currently reports 44 applied rows, from `20261008184418` through `20261024181559`. Exact version/name rows were read from `supabase_migrations.schema_migrations`. At least these applied entries do not exist at their exact expected version/name paths under `supabase/migrations/`: `20261015185018_reactivate_removed_cashier_identity.sql`, `20261015185332_reactivate_removed_cashier_identity.sql`, `20261015185405_reactivate_removed_cashier_identity.sql`, `20261016125950_allow_reinvite_removed_cashier_same_branch.sql`, `20261016131840_allow_reinvite_same_local_user_activation_history.sql`, `20261018140123_add_financial_reporting_inventory_rpc.sql`, `20261023044205_retire_cashier_feature.sql`, `20261023045447_remove_staff_auth_rate_limits.sql`, `20261023045544_remove_cashier_customer_sync_rpcs.sql`, `20261023050312_purge_cashier_notifications.sql`, `20261023052001_restore_historical_actor_user_ids.sql`, `20261024174802_capture_financial_operation_collisions.sql`, and `20261024181559_repair_admin_customer_directory_sync_after_rpc_retirement.sql`. The repository migration README says the historical files are aligned, so this discrepancy needs resolving: filenames may have been renamed, but the exact expected paths were not found. Earlier migration files checked by exact path were present.
9. **Repo-only migrations not applied:** this list is **not yet established**. The connected GitHub file interface used for this pass can fetch known paths but did not provide a complete `supabase/migrations/` directory listing. Do not treat “not established” as “none.”
10. **Live schema/function/trigger comparison is partial.** Read-only catalog queries confirmed live functions including `public.fetch_financial_reporting_inventory_v1`, `public.ingest_financial_envelope`, `public.fetch_financial_envelopes_v1/v2/v3`, customer-directory RPCs, and live triggers on financial envelopes, staff identities, branches, memberships, businesses, and profiles. The live inventory RPC has no source at the expected migration path above. A full exhaustive mapping of every live table/function/trigger to a specific repo migration was not completed; therefore no blanket “no drift” conclusion is justified.
11. **Open business-policy questions:** should opening float count toward expected cash; should report Credit Outstanding be an as-of ledger balance or period activity; should coupon purchases count as sales revenue or remain a separate stored-value liability; should report period boundaries follow event timestamps (current projection) or restate the original sale; which tax rounding mode and split allocation rule are the business standard; and should a coupon-funded sale be corrected through refund-to-coupon or another explicitly supported correction path.
